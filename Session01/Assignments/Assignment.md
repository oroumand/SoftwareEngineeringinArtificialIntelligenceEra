# تمرین جلسهٔ اول — مهندسی نرم‌افزار مبتنی بر مشخصات (SDD)

**موضوع:** Spec Kit + Coding Agent  
**پروژهٔ عملی:** ChangeFlow — سامانهٔ مدیریت درخواست تغییر  
**موعد تحویل:** تا جلسهٔ آینده  
**فناوری:** آزاد؛ C#/.NET، Java/Spring Boot، JavaScript/Node.js یا فناوری آشنای دیگر

هدف تمرین این است که توانایی تحلیل نیازمندی، تصمیم‌گیری معماری، مدیریت فرایند توسعه با Coding Agent و ارائهٔ شواهد صحت کار سنجیده شود؛ نه صرفاً مقدار کد تولیدشده.

---

## بخش اول — سؤالات مفهومی (۵ سؤال)

**راهنما:** پاسخ‌ها را تحلیلی و با زبان خودتان بنویسید. تعریف اصطلاحات یا کپی از مستندات کافی نیست. در صورت نیاز از مثال فنی در Stack خودتان استفاده کنید.

### سؤال ۱ — Constitution و حاکمیت معماری

تیم شما تصمیم گرفته تمام Business Logic در لایهٔ Domain یا Application قرار بگیرد و API فقط مسئول دریافت درخواست و ارائهٔ پاسخ باشد.

Coding Agent یک قابلیت را پیاده‌سازی کرده و همهٔ Testها موفق شده‌اند؛ اما بخشی از Business Logic مستقیماً داخل Controller یا Endpoint نوشته شده است.

- چه تفاوتی بین موفقیت Testها و رعایت اصول معماری وجود دارد؟
- قاعدهٔ جداسازی مسئولیت‌ها باید در Constitution، Plan یا Tasks ثبت شود؟ چرا؟
- چگونه می‌توان در توسعه‌های بعدی از تکرار این مشکل جلوگیری کرد؟

### سؤال ۲ — Specify و Clarify

مالک محصول می‌گوید:

> «کارمندان بتوانند درخواست ثبت کنند و مدیرها بعد از بررسی، درخواست‌ها را تأیید کنند.»

Coding Agent فرض می‌کند هر مدیری می‌تواند درخواست خودش را نیز تأیید کند.

- آیا Agent مجاز است این تصمیم را بدون تأیید مالک محصول نهایی کند؟
- تفاوت Assumption با تصمیم تأییدشدهٔ مالک محصول چیست؟
- حداقل دو ابهام مهم دیگر در این درخواست پیدا کنید.
- کدام ابهام‌ها باید در Specify برجسته شوند و Clarify چه نقشی در رفع آن‌ها دارد؟

### سؤال ۳ — Requirement در برابر Design Decision

در Specification آمده است:

> «هیچ درخواست تأییدشده‌ای نباید با محتوای تغییرکرده، بدون بررسی و تأیید معتبرِ آن محتوا، اجرا شود.»

توسعه‌دهنده پیشنهاد می‌کند یک فیلد عددی به نام `ContentRevision` اضافه کنیم.

- کدام بخش Requirement است و کدام بخش Design Decision؟
- چرا بهتر است مکانیزم فنی در Plan/Research بررسی شود؟
- حداقل دو راهکار جایگزین برای تشخیص محتوای تأییدشده پیشنهاد کنید و Trade-off آن‌ها را توضیح دهید.

### سؤال ۴ — Tasks و Analyze

برای یک Feature، تعداد ۳۰ Task تولید شده و هر Requirement حداقل به یک Task مرتبط است. با این حال، یک Task به دیتابیس آماده نیاز دارد، در حالی که Migration دیتابیس در Task بعدی تعریف شده است. همچنین دو Task دارای نشانگر `[P]` باید فایل مشترکی را تغییر دهند.

- چه مشکلاتی در Dependency و Parallelism وجود دارد؟
- انتظار دارید Analyze چه Findingهایی گزارش کند؟
- آیا پوشش ۱۰۰٪ Requirementها توسط Tasks، آمادگی قطعی برای Implement را ثابت می‌کند؟ چرا؟

### سؤال ۵ — Implement، Validation و Converge

Coding Agent گزارش داده است:

> «تمام Taskها تکمیل شده‌اند؛ پروژه Build شده و ۱۲۰ Test همگی Passed هستند.»

اما در Code Review متوجه می‌شوید یک قاعدهٔ امنیتی رعایت نشده و یک معیار پذیرش انسانی هنوز ارزیابی نشده است.

- آیا Feature قابل اعلام به‌عنوان «کامل و پذیرفته‌شده» است؟
- تفاوت Build، Test، Validation و Acceptance چیست؟
- Converge در این وضعیت چه نقشی دارد و چه تفاوتی با Analyze دارد؟
- اگر Converge شکاف جدیدی پیدا کند، مسیر اصلاح چیست؟

## بخش دوم — پروژهٔ عملی ChangeFlow

### ۱. صورت مسئله

یک شرکت نرم‌افزاری به سامانه‌ای برای مدیریت **درخواست‌های تغییر (Change Requests)** نیاز دارد. کارمندان می‌توانند درخواست‌هایی مانند افزودن قابلیت، اصلاح فرایند یا تغییر API ثبت کنند. درخواست‌ها پیش از تأیید نهایی باید بررسی شوند و هیچ‌کس نباید درخواست خودش را تأیید کند.

**هدف:** با استفاده از Spec Kit و یک Coding Agent، نسخهٔ اولیهٔ این سامانه را بر اساس روش SDD تحلیل، طراحی، پیاده‌سازی و اعتبارسنجی کنید.

این پروژه قرار است در جلسات آینده گسترش پیدا کند؛ بنابراین معماری را **ساده، قابل نگهداری و قابل توسعهٔ تدریجی** طراحی کنید. قابلیت‌های AI، RAG، MCP و Multi-Agent فعلاً جزو Scope این تمرین نیستند.

### ۲. نقش‌ها و داده‌های پایه

سامانه حداقل دو نقش دارد:

- **Requester:** ثبت‌کنندهٔ درخواست تغییر
- **Reviewer:** بررسی‌کننده و تأییدکنندهٔ درخواست

هر Change Request حداقل شامل عنوان، شرح تغییر، دلیل تغییر، شناسهٔ ثبت‌کننده و وضعیت فعلی است. در صورت نیاز می‌توانید اطلاعات دیگری را با دلیل مشخص به طراحی اضافه کنید.

### ۳. گردش وضعیت‌ها

```text
Draft ──Submit──> PendingReview ──Approve──> Approved
                           │
                           └──RequestChanges──> ChangesRequested
                                                   │
                                                   └──Submit──> PendingReview
```

**قواعد قطعی محصول:**

1. Requester می‌تواند درخواست جدیدی در وضعیت `Draft` ثبت کند، Draft خود را ویرایش کند و آن را برای بررسی ارسال کند.
2. Reviewer می‌تواند درخواستِ در انتظار بررسی را تأیید کند یا برای اصلاح برگرداند.
3. **Self-Approval ممنوع است**؛ حتی اگر یک کاربر هم‌زمان هر دو نقش را داشته باشد.
4. درخواست برگشت‌خورده قابل اصلاح و ارسال مجدد است.
5. درخواست `Approved` قابل ویرایش نیست.
6. عملیات تغییر وضعیت باید هویت، مجوز فعلی و وضعیت درخواست را بررسی کنند.
7. درخواست‌های هم‌زمان نباید باعث بازنویسی بی‌صدای تغییرات جدیدتر یا ایجاد وضعیت ناسازگار شوند.

**موارد نیازمند تصمیم‌گیری:** هر رفتاری که در صورت مسئله مشخص نشده، مثلاً حذف Draft، فهرست‌کردن درخواست‌های دیگران، نحوهٔ لغو مجوز یا رفتار درخواست تکراری، باید در Specify/Clarify تعیین تکلیف یا به‌صورت Assumption قابل بازبینی ثبت شود. این تصمیم‌ها را بدون توضیح به Coding Agent واگذار نکنید.

### ۴. محدودهٔ فنی

- انتخاب Stack آزاد است: **.NET، Java، JavaScript/Node.js** یا فناوری آشنای دیگر.
- ارائهٔ یک **HTTP API** کافی است و Frontend الزامی نیست.
- یک روش Persistence قابل اجرا انتخاب کنید و دلیل انتخاب را در Research بنویسید.
- مکانیزم Authentication/Authorization و Concurrency را با توجه به شرایط پروژه انتخاب و مستند کنید.
- ایجاد لایه‌ها و Abstractionهای اضافی بدون نیاز واقعی امتیاز مثبت ندارد.
- از یک Coding Agent استفاده کنید، اما تصمیم‌های محصولی و معماری را با مسئولیت خودتان بازبینی کنید.

### ۵. مراحل مورد انتظار SDD

| مرحله | کار مورد انتظار | شواهد یا Artifact |
|---|---|---|
| **Init** | آماده‌سازی Spec Kit برای Agent انتخاب‌شده | ساختار و تنظیمات پروژه |
| **Constitution** | قواعد معماری، امنیت، کیفیت و توسعهٔ تدریجی | `.specify/memory/constitution.md` |
| **Specify** | User Stories، Functional Requirements، Acceptance Scenarios و Success Criteria | `spec.md` |
| **Clarify** | شناسایی و حل ابهام‌های اثرگذار؛ ثبت تصمیم‌ها و فرض‌ها | بخش Clarifications و اصلاح Spec |
| **Plan / Research** | معماری، مدل داده، قرارداد API، Persistence و Concurrency؛ مقایسهٔ گزینه‌ها | `plan.md`، `research.md`، `data-model.md`، `contracts/` |
| **Tasks** | تجزیهٔ کار، تعیین وابستگی‌ها و موارد قابل موازی‌سازی | `tasks.md` |
| **Analyze** | بررسی سازگاری Spec/Plan/Tasks و اصلاح مشکلات مهم | گزارش Findings و تغییرات اصلاحی |
| **Implement** | پیاده‌سازی مرحله‌ای API طبق Taskها | سورس کد، وضعیت Taskها |
| **Build / Test / Validation** | اجرای آزمون‌ها و ثبت نتیجهٔ واقعی | دستور اجرا و خروجی قابل بررسی |
| **Converge** | بررسی شکاف میان کد فعلی و Intent مستند | گزارش Gapها و Taskهای اصلاحی احتمالی |

توجه کنید: **Analyze در نسخهٔ مورد استفاده یک بررسی Read-only است. Converge نیز برای اصلاح مستقیم کد نیست؛ در صورت نیاز کار باقی‌مانده را به Task قابل ردیابی تبدیل می‌کند.**

### ۶. حداقل آزمون‌های ضروری

آزمون خودکار باید دست‌کم این سناریوها را پوشش بدهد:

1. ایجاد موفق درخواست در وضعیت `Draft`.
2. انتقال `Draft` به `PendingReview` با Submit معتبر.
3. رد تأیید درخواست توسط خود ثبت‌کننده، حتی با داشتن نقش Reviewer.
4. تأیید موفق توسط Reviewer مجاز و مستقل.
5. رد ویرایش درخواست `Approved`.
6. جلوگیری از بازنویسی بی‌صدای تغییر جدیدتر توسط درخواست مبتنی بر Version قدیمی.

علاوه بر نتیجهٔ HTTP، در آزمون‌های حساس وضعیت ذخیره‌شدهٔ داده‌ها را نیز بررسی کنید. می‌توانید آزمون‌های بیشتری برای مجوز، انتقال وضعیت نامعتبر، Race Condition و خطاهای Persistence اضافه کنید.

### ۷. اقلام تحویلی

تا جلسهٔ آینده موارد زیر را ارسال کنید:

- **لینک Repository** قابل بررسی.
- Artifactهای SDD تولیدشده و اصلاح‌شده در مراحل بالا.
- سورس کد و فایل‌های لازم برای اجرای API.
- **گزارش واقعی Build و Test** شامل فرمان‌ها، تعداد آزمون‌های اجراشده و نتیجهٔ آن‌ها.
- **گزارش Analyze** شامل Findings و تصمیم اصلاحی هر مورد مهم.
- **گزارش Converge** شامل نتیجهٔ واقعی، شکاف‌های باقی‌مانده و Taskهای جدید احتمالی.
- `README.md` شامل Stack، پیش‌نیازها، روش اجرا، تصمیم‌های اصلی معماری، محدودیت‌های شناخته‌شده و نقش Coding Agent.
- پاسخ پنج سؤال مفهومی، در فایلی مانند `docs/answers/session-01.md`.

**مهم:** اگر بخشی تکمیل نشده، وضعیت واقعی را صریح اعلام کنید. گزارش ساختگی از اجرای Test، پذیرش انسانی یا خروجی Agent قابل قبول نیست. اگر Converge Task تازه‌ای ایجاد کرد، اجرای تمام Taskهای جدید برای موعد فعلی الزامی نیست، اما ثبت و تحلیل آن‌ها لازم است.

### ۹. نکتهٔ پایانی

انتظار نداریم همهٔ دانشجوها ساختار کد یا فناوری یکسان داشته باشند. موضوع اصلی این است که **بتوانید از نیازمندی اولیه تا تصمیم معماری، Task اجرایی، کد تولیدشده و شواهد آزمون، یک زنجیرهٔ قابل ردیابی و قابل دفاع ارائه کنید.**

پروژهٔ ChangeFlow در جلسات بعدی با Featureهای جدید توسعه پیدا خواهد کرد؛ بنابراین از پیاده‌سازی زودهنگام قابلیت‌های خارج از Scope خودداری کنید.
